# Agent 系統規劃書（v2 草案）— 全新獨立專案

> 目的：把九個子系統（文案／客服／活動企劃／廣告／業務開發／視覺／數據分析／營運／稽核）
> 規劃成「可獨立運作、也可互相協作」的 Agent 架構。
> 請直接在本文件上批註需要修改的地方。

> **⚠️ 專案定位（v2 重點修正）**：這是一個**全新的獨立專案**，與既有的 Anima 個人儀表板
>（投資、習慣、待辦等 widget）**完全分離** —— 不共用程式碼、不共用資料、不共用部署。
> 本文件暫放在 Anima repo 只是為了方便批註，新專案 repo 建立後即搬移過去。

## 1. 整體架構：三層 + 共用基礎設施

```
┌─────────────────────────────────────────────┐
│  指揮層：營運 Agent（決策大腦）                 │
│  產品｜採購｜定價｜成本｜行銷｜財務              │
└──────────────────┬──────────────────────────┘
                   │ 下目標、派任務、收報表
┌──────────────────┴──────────────────────────┐
│  執行層（可獨立呼叫、也可被指揮層調度）           │
│  文案｜視覺｜廣告｜活動企劃｜客服｜業務開發｜數據分析 │
└──────────────────┬──────────────────────────┘
                   │ 所有「對外」輸出
┌──────────────────┴──────────────────────────┐
│  監督層：稽核 Agent + 人工審核佇列              │
│  L0 自動放行 / L1 Agent 自審 / L2 本人核准      │
└─────────────────────────────────────────────┘
```

### 共用基礎設施（所有 Agent 都依賴，建議第一期就建）

1. **資料庫**（建議 Postgres，如 Supabase/Neon）
   - `tasks`：任務佇列（誰派的、給哪個 Agent、狀態、產出連結）
   - `crm_contacts`：業務開發名單 + 客服對話歸戶
   - `assets`：素材庫（文案、圖片、版型，含版本與成效標記）
   - `approvals`：審核佇列與紀錄
   - `metrics`：各渠道每日數據快照（給數據分析用）
2. **品牌知識庫**：品牌語調（tone of voice）、產品資訊、價格表、過往高成效素材範例、禁用語。所有產出型 Agent 的共同輸入，沒有它每個 Agent 的產出都會不穩定。
3. **排程器**：每日/每週/每月觸發（報表、電子報、廣告巡檢）。
4. **控制台（新專案自己的前端）**：任務看板、審核佇列、報表頁。你每天打開就能批「待核准」的項目。這是新專案的 UI，不是 Anima 的頁面。

**「可獨立、可協作」的實現方式**：每個 Agent 是一個獨立模組，對外只有兩個介面 ——
(a) 直接呼叫（你在控制台上單獨叫文案 Agent 寫一篇貼文）；
(b) 任務佇列（其他 Agent 把任務寫進 `tasks`，它領走執行）。
這樣不互相依賴程式碼，只共享資料庫，任何一個壞了其他照常運作。

## 2. 各子系統詳細規劃

### 2.1 文案 Agent

| 項目 | 內容 |
|---|---|
| 職責 | 社群貼文、廣告文案、部落格長文、電子報文案、官網文案結構 |
| 輸入 | 品牌知識庫 + 任務需求（主題、渠道、目標受眾、檔期） |
| 輸出 | 文字稿 + 結構（標題層級、CTA 位置），存入 `assets`，狀態 = 待審 |
| 協作 | 高成效素材由數據分析 Agent 回寫標記，形成「越寫越準」的迴圈 |

**建議調整**：你原本把 Banner、DM、PDF、電子報「設計」放在文案底下。
建議拆開 —— 這四項是「文案 × 視覺」的協作產物：文案 Agent 出文字與版面結構，
**視覺 Agent 負責落版輸出**（用 Canva 模板）。否則文案、視覺兩個 Agent 職責重疊，以後很難維護。

### 2.2 視覺 Agent

| 項目 | 內容 |
|---|---|
| 職責 | Banner、DM、PDF、電子報版型、廣告素材圖、官網視覺 |
| 串接 | **Canva（主力，建議）**：品牌套件、模板、一鍵輸出多尺寸（FB/IG/Google 各版位規格表內建）。**Figma（輔助）**：官網 UI、設計系統 |
| 輸入 | 文案 Agent 的稿件 + 品牌套件 + 各渠道尺寸規格 |
| 輸出 | 成品圖/PDF 存入 `assets`，狀態 = 待審 |

Canva 與 Figma 都已有現成 MCP 整合，不用自己寫 API 串接，這部分成本很低。

### 2.3 廣告 Agent（FB + Google）

| 項目 | 內容 |
|---|---|
| 現成基礎 | FB Marketing API 串接可從 Anima 複製過來改（那邊已驗證能跑），Google Ads API 需新寫 |
| 功能 1：投放策略 | 讀營運目標 + 歷史數據 → 產出受眾/版位/出價策略提案 |
| 功能 2：素材規劃 | 開素材需求單 → 自動派任務給文案、視覺 Agent |
| 功能 3：預算規劃 | 月預算 → 各 campaign 分配 → 每日巡檢（ROAS、CPA 異常告警） |
| 功能 4：自動化規則 | 例：ROAS < 門檻連續 3 天 → 提案暫停（**進審核佇列，不直接執行**） |

**安全閥（強烈建議）**：任何「會花錢或停錢」的動作一律 L2 人工核准；
只有「讀數據、產報告、開素材需求單」可自動執行。等系統穩定再逐步下放權限。

### 2.4 數據分析 Agent

| 項目 | 內容 |
|---|---|
| 資料來源 | FB/Google 廣告、GA4、客服對話統計、CRM 漏斗、（若有電商）Shopify |
| 排程產出 | **每日**：廣告快訊（花費/ROAS/異常）→ Slack 或 Email。**每週**：成效週報（素材排行、受眾洞察）→ Notion/PDF。**每月**：營運月報（渠道 ROI、成本結構）→ PDF + 給營運 Agent 當決策輸入 |
| 關鍵設計 | 每天把各 API 數據快照存進 `metrics` 表，報表從自己的資料庫產生，不要每次都打外部 API（會被限流、歷史數據也拿不回來） |

### 2.5 客服 Agent

| 項目 | 內容 |
|---|---|
| 通路 | 待你確認：LINE 官方帳號？FB Messenger？網站 widget？（台灣場景建議 LINE 優先） |
| 架構 | FAQ/產品知識庫 → 機器人先答 → 信心不足或客訴 → 轉真人 + Slack 通知 |
| 回流 | 對話歸戶到 CRM；常見問題統計給數據分析；產品抱怨給營運 Agent |

### 2.6 活動企劃 Agent

| 項目 | 內容 |
|---|---|
| 定位 | 「協調型」Agent —— 它本身不產素材，產**企劃案**並拆解任務 |
| 輸入 | 營運目標（如：母親節檔期、預算 X、目標營收 Y） |
| 輸出 | 企劃案（活動機制、時程、預算分配、KPI）→ 你核准後 → 自動拆成任務派給文案/視覺/廣告 |

### 2.7 業務開發 Agent

| 項目 | 內容 |
|---|---|
| 流程 | 蒐集潛在客戶名單 → 清洗/去重 → 進 CRM → 名單評分 → 電子報/開發信 → 業務跟進 pipeline |
| CRM 欄位 | 公司、聯絡人、來源、產業、評分、開發階段（陌生→已寄信→已回覆→洽談→成交）、負責業務 |
| 電子報 | 串 Gmail 或 ESP（如 Mailchimp/Brevo），開信/點擊數據回流數據分析 |

**⚠️ 必須先確認的法遵問題**（以爬取設計師公會會員名單為例）：
1. 台灣《個資法》：蒐集個資需符合特定目的，首次行銷接觸需提供免費拒絕方式，對方拒絕後不得再行銷。
2. 來源網站的服務條款是否允許自動化抓取（公會網站通常會限制）。
3. 寄送行銷郵件必須有退訂機制，否則網域很快被列入垃圾郵件黑名單，反而傷害整個電子報系統。

**建議做法**：優先以「公開商業資訊」（公司官網、政府公開的公司登記、有公開授權的名錄）為來源，
名單進 CRM 時記錄來源欄位，首封信即附退訂連結。這個 Agent 建議排最後一期做，先把合規流程定好。

### 2.8 營運 Agent（決策大腦）

| 模組 | 職責 | 輸入 |
|---|---|---|
| 產品 | 品項表現、上下架建議 | 銷售數據、客服回饋 |
| 採購 | 補貨提醒、供應商比較 | 庫存、交期、銷售預測 |
| 定價 | 毛利試算、調價提案 | 成本、競品、銷量彈性 |
| 成本 | 成本結構監控、異常告警 | 採購、廣告、營運費用 |
| 行銷 | 季度行銷目標、檔期規劃 | 數據分析月報 |
| 財務 | 現金流、損益快照 | 全部數據彙整 |

**定位釐清**：營運 Agent 是「讀報表 → 提決策建議 → 派任務」的指揮者，不直接執行任何對外動作。
**財務與定價類決策建議永遠維持 L2 人工核准**，這層不建議自動化。
六個模組不用一次做完 —— 建議先做「行銷 + 成本」兩個（跟廣告系統閉環），其他四個視業務型態再加。

### 2.9 稽核 Agent（監督層）

雙層機制：**規則引擎**（硬規則，例如：金額 > 0 一律送審、含敏感詞攔下）＋ **LLM 審核**（品牌語調、事實正確性、合規檢查）。

| 等級 | 定義 | 預設範圍（待你確認） |
|---|---|---|
| L0 | 自動放行 | 內部報表、數據快照、任務指派 |
| L1 | 稽核 Agent 自審通過即放行 | 例行社群貼文？（初期建議也走 L2） |
| L2 | 必須本人核准 | 對外發布、任何花錢動作、寄信給客戶、改價 |

所有審核紀錄存 `approvals` 表，控制台上有審核佇列頁面 + 每日待審摘要推播（Slack/Email）。
**初期建議全部 L2，跑一個月後再根據錯誤率逐項下放到 L1/L0** —— 這比一開始就開放再收回安全得多。

## 3. 協作流程範例：一檔母親節活動

1. **營運**：設定檔期目標（預算 10 萬、目標營收 50 萬）→ 派任務給活動企劃
2. **活動企劃**：產出企劃案 → **稽核 L2** → 你核准
3. 企劃自動拆任務：**文案**（貼文 ×6、廣告文案 ×4、EDM ×1）＋ **視覺**（Banner ×4、EDM 版型）＋ **廣告**（投放計畫）
4. 素材完成 → **稽核 L2** → 你核准 → 廣告 Agent 建立 campaign（再核准一次才開跑）
5. **數據分析**：每日快訊；**廣告**：巡檢，異常時提案調整（核准後執行）
6. 檔期結束：數據分析產結案報告 → 營運 Agent 歸檔、更新下次決策依據

## 4. 技術架構選項（需要你決定）

| 方案 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A. 自建 | Claude Agent SDK 寫 orchestrator + 各 Agent | 彈性最高、邏輯完全自控 | 開發量最大 |
| B. Make/n8n | 排程、串接、審核流程全用自動化平台 + LLM 節點 | 最快上線、串接現成 | 複雜推理與多輪協作受限 |
| C. 混合（**建議**） | 排程/webhook/通知用 Make；推理與產出用 Agent SDK；新專案自帶控制台前端 | 兩邊取長 | 兩套系統要維護 |

不論選哪個方案，**第一天就建資料庫**（建議 Supabase：Postgres + Auth + 排程都有）。

## 5. 建議分期

| 期 | 內容 | 理由 |
|---|---|---|
| Phase 1 | 新 repo + 資料庫 + 控制台骨架（任務看板/審核佇列）+ 品牌知識庫 + **文案 + 視覺** | 基礎設施一次到位；文案×視覺最快有感、風險最低 |
| Phase 2 | **廣告 + 數據分析** | FB 串接從 Anima 複製改寫，補 Google Ads + metrics 快照即可閉環 |
| Phase 3 | **客服 + 活動企劃** | 客服要先定通路；活動企劃需要前面的 Agent 都在才有東西可調度 |
| Phase 4 | **業務開發 + 營運大腦** | 業務開發先過法遵；營運大腦需要累積幾個月數據才有決策依據 |

稽核不是一期 —— 從 Phase 1 第一天就存在（最小版：所有對外輸出進審核佇列）。

## 6. 需要你確認的決策點

1. **專案名稱與新 repo**：新專案叫什麼？確認後開新 repo，本規劃書搬過去，與 Anima 徹底分開。
2. **技術路線**：方案 A / B / C？（建議 C）

4. **客服通路**：LINE / Messenger / 網站 widget，先做哪個？
5. **稽核預設**：初期全 L2 你 OK 嗎？哪些項目你希望一開始就自動放行？
6. **業務開發名單來源**：能否改用公開商業資訊？公會名單部分需先確認取得方式合規。
7. **視覺主力**：Canva 為主、Figma 為輔，這樣分工可以嗎？
8. **CRM**：自建在新專案的資料庫裡（建議，反正要建 DB）還是接現成服務（HubSpot/Notion）？
9. **營運六模組**：先做行銷 + 成本，其他四個後補，可以嗎？
10. **通知偏好**：每日待審摘要與異常告警走 Slack 還是 Email？
